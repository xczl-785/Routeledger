# RouteLedger 0.9.5 Agent 工具面评审与任务板

## 文档目的

本文记录 `feature/plugin-compliance-cleanup` 分支将公开 MCP 工具收敛为任务型工具的评审结论、Agent 使用方影响、发布阻塞项、实施顺序和验收标准。

评审结论：架构方向通过，发布准备未通过。当前实现适合作为 0.9.5 候选继续迭代，不应在使用方迁移和安装验收闭环前发布。

## 变化摘要

公开工具面调整为：

- 只读：`inspect_runtime`、`inspect_route`。
- 配置：`configure_binding`、`configure_project`。
- 当前工作：`manage_todo`、`manage_deferred`、`manage_constraint`。
- 路线：`propose_route_change`、`set_version_state`、`execute_route_change`。
- UI：`manage_mission_control`。

多工作流工具统一用 `operation` 选择分支。旧低层 handler 仍作为内部 capability 保留，由公共 Facade 分派；持久化模型、JSON-first 边界、版本门禁和 L3 `actionType` 不迁移。host binding 配置渲染/写入退出 Agent 公共工具面，保留给 CLI/安装流程。

风险面固定为 2 个只读、8 个普通写和 1 个高风险工具。`execute_route_change` 是唯一公开高风险入口。

## 架构评价

### 优点

1. Agent 先选择任务领域，再选择具体 `operation`，比直接在几十个相近低层名称中选择更清楚。
2. MCP 公共协议与内部 application/capability 分离，避免为公共工具改名而重写领域服务。
3. Proposal、approval/rejection、commit 和强制关闭收敛到单一高风险边界，宿主审批策略更容易审计。
4. 所有写入继续经过 binding preflight、`expectedRouteLedgerRoot` 断言、RouteLedgerService 和 JSON-first 存储边界。
5. 工具建议和错误恢复中的旧名称会投影为新工具名与 `operation`，有利于 Agent 自恢复。
6. 公开响应统一为 `ok/data/error/meta` envelope，并发布 `outputSchema`。

### 代价与风险

1. 11 个工具仍承载约 47 个工作流。当前公开 input schema 总量约 58.8 KB；`inspect_route`、`propose_route_change`、`execute_route_change` 分别约为 16.5 KB、15.5 KB、8.2 KB。工具排序负担下降，但参数分支判断和上下文成本没有同比下降。
2. 顶层 `oneOf` 对模型和 MCP 客户端的 Schema 支持提出更高要求。Agent 必须同时选对工具、`operation` 和该分支允许的字段。
3. 公共 `outputSchema` 当前主要验证 envelope，`data` 仍为任意结构。内部 capability 的细粒度输出 Schema 没有在组合分支执行路径中得到等价验证。
4. 工具描述被显著压缩后，operator Skill 和 server instructions 成为正确调用的重要组成部分；两者一旦漂移，会直接影响 Agent。

## Agent 使用方评审

### 预期改善

- 工具发现更稳定：查询、配置、工作项、路线和 UI 形成清楚的一级分类。
- `operation` 与业务字段 `action` 解耦，避免 Deferred review 等业务动作与路由分派冲突。
- 统一 envelope 便于 Agent 判断成功、业务失败和安全重试。
- 公开错误恢复动作指向真实可见的新工具，不再推荐隐藏的内部工具。
- 高风险入口唯一，降低 Agent 把“提出变更”和“提交变更”混淆的概率。

### 当前阻塞

1. server instructions 仍写 `action=runtime` 和 `action=open`，但 Schema 和 Skill 要求 `operation`。
2. 非法 operation 的异常仍使用“Unknown ... action”措辞，术语未收口。
3. Git marketplace smoke 仍调用 `init_project`、`get_runtime_context`，导致三平台安装验收失败。
4. Codex host smoke 仍要求 Agent 调用 `get_runtime_context`。
5. `examples/config/codex.config.toml` 的 allowlist 和 approval 配置仍引用旧名称。
6. 部分测试/fixture 脚本仍直接调用旧 registry 名称。
7. 当前 CI 失败意味着没有一条通过的安装后端到端证据证明真实 Agent 能发现并使用新的 11 工具面。

## 建议

### P0：发布阻塞

- 统一所有 Agent-facing 文案为 `operation`，消除 server instructions 与 Skill 冲突。
- 更新 marketplace smoke、host Agent smoke、fixtures 和示例配置到新工具面。
- 增加安装后 `tools/list` 精确验证：只暴露 11 个工具，并实际调用 `inspect_runtime(operation="runtime")` 与 `configure_project(operation="initialize")`。
- 恢复 Windows、Ubuntu、macOS marketplace ingestion smoke。

### P1：协议完整性

- 组合工具在选定分支后，使用内部 capability 的 output schema 校验 handler 返回值；公共 envelope 校验继续保留。
- 为分支级输出漂移增加 RED/GREEN 回归测试，确认错误被转换为 `INVALID_TOOL_OUTPUT`，且不泄漏无效 structured content。
- 评估是否需要在公开 Schema 中发布分支数据 union；若体积过大，至少保证服务器内部逐分支验证。
- 给公共工具引用投影增加契约测试，确保 recovery 中不会出现不可见旧工具名。

### P2：Agent 体验与演进

- 用至少两档 Agent 模型测量工具选择、operation 选择、一次调用成功率和修复重试率。
- 记录 tools/list 的 Schema 字节数和描述长度预算，避免以后只追踪工具数量。
- 如果 `inspect_route` 或 `propose_route_change` 的分支错误率明显偏高，再基于数据拆分；不把“固定 11 个”当作不可改变的目标。

## 实施顺序

1. 先修复测试客户端、示例配置和 Agent-facing 术语，使候选工具面能被真实消费者调用。
2. 再增强组合分支输出校验；该项会触及 Facade 核心，放在公共工具面基线明确之后。
3. 完成一个批次后统一执行静态检查、定向单测、workspace quality、插件 smoke、marketplace smoke。
4. 验收通过后更新本文任务状态、遗留风险和发布建议。
