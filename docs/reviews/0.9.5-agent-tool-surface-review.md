# RouteLedger 0.9.5 Agent 工具面评审与任务板

## 结论

`feature/plugin-compliance-cleanup` 将公开 MCP 工具按 Agent 的任务意图组织。工具数量不是硬指标；名称可理解性、单工具职责内聚和安全边界优先。

当前目标工具面为 15 个工具：

- 只读：`inspect_runtime`、`inspect_route_progress`、`inspect_versions`、`inspect_l3_route_operations`。
- 配置：`configure_binding`、`configure_project`。
- 当前工作：`manage_todo`、`manage_deferred`、`manage_constraint`。
- 变更提案：`propose_version_lifecycle_change`、`propose_version_structure_change`、`propose_l3_route_change`。
- 状态与执行：`set_version_state`、`execute_route_change`。
- 本机 UI：`manage_mission_control`。

风险分布为 4 个只读、10 个普通写和 1 个高风险工具。`execute_route_change` 仍是唯一公开高风险入口。

## 命名审核

命名标准是：Agent 仅看工具名，就能判断它查询或改变什么对象，以及它是否只是提出变更。

| 工具 | 功能范围 | 命名理由 |
| --- | --- | --- |
| `inspect_route_progress` | 当前上下文、下一步、文档漂移、Version 收尾摘要与计划 | `progress` 能覆盖推进和收尾；`work` 容易被误解为 Todo 列表。 |
| `inspect_versions` | Version 列表、窗口、结构、门禁和迁移指南 | 复数对象自然覆盖单 Version 检查和跨 Version 结构。 |
| `inspect_l3_route_operations` | L3 授权状态、授权建议和提案查询 | 同时说明层级、对象和查询范围，避免含糊的 `inspect_l3`。 |
| `propose_version_lifecycle_change` | 批量、状态迁移、推进和关闭的预检/提案 | 明确它改变生命周期，并保留“只是提出”的语义。 |
| `propose_version_structure_change` | 创建、插入、创建子 Version 和重排提案 | 明确它改变路线结构，不会被理解为立即创建。 |
| `propose_l3_route_change` | 创建一个精确 L3 路线变更提案 | 单一功能直接暴露，不再要求冗余的 `operation` 选择。 |

应避免 `manage_versions`、`inspect_route_work`、`inspect_l3`、`create_version`、`close_version` 这类名称：它们会混淆读写权限、缩窄实际范围，或把提案误说成立即执行。

## 工具重量变化

旧的任务型公开面有 11 个工具、47 个 operation 分支，输入 Schema 总量约 58.8 KB。最大两个工具分别有 16 和 9 个分支。

拆分后公开工具为 15 个，最大单工具分支降到 6。Schema 总量不会明显下降，因为相同业务字段仍需对 Agent 可见；改善主要来自：

- 工具名先完成一次领域筛选。
- Agent 不必在一个宽泛工具里扫描大量无关 operation。
- 只读查询、普通提案和高风险执行的心智边界更清楚。
- 单功能 L3 提案不再携带无意义的二次分派字段。

因此，本次优化目标是减少选择歧义，而不是追求 tools/list 的最小字节数。

## Agent 使用方评价

对能力较强的 Agent，拆分降低了阅读无关 Schema 的成本，尤其是 Version 查询、L3 查询和普通路线变更之间不再混在一起。

对中等能力 Agent，收益更明显：工具名已经包含对象和意图，先选错大类的概率下降；单工具 operation 最多 6 个，也更容易一次生成正确参数。

仍需注意：

- 写入和高风险调用仍必须携带匹配的 `expectedRouteLedgerRoot`。
- `propose_version_lifecycle_change` 的部分 operation 同时支持 preview/preflight 与 propose，Agent 仍需正确选择 `mode`。
- L3 必须遵守 propose、decision、commit/reject 的精确链路。
- `manage_mission_control` 是本机 UI 副作用，不是 canonical RouteLedger 数据写入，必须继续单独隔离。

## 安全与架构边界

- 所有 canonical 写入继续经过 binding preflight、根目录断言、`RouteLedgerService` 和 JSON-first 存储边界。
- `execute_route_change` 不拆分。强制关闭与 L3 execute/approve/commit/reject 继续共享唯一 host 高风险准入面。
- L3 proposal、decision、approval artifact、digest、root binding 和 single-use commit 规则不变。
- 内部 capability 可以保留细粒度名称；它们不是 Agent 的公开兼容接口。
- 公共响应继续使用统一 envelope，并在选中 composite 分支后验证内部 capability 的 output schema。
- `configure_binding` 是会话控制面；`manage_mission_control` 是本机诊断/UI 面，二者不得并入普通 canonical 写工具。

## 实施顺序

1. 用失败契约测试锁定 15 个公开工具名、风险分布和唯一高风险入口。
2. 拆分查询与普通提案 facade，保持内部 capability 和持久化语义不变。
3. 迁移测试 helper、Agent-facing fixture、配置示例、Skill、server instructions 和 package/plugin smoke。
4. 同步生成的插件 runtime 与 release metadata。
5. 在一个完整批次后集中执行静态检查、测试、插件 smoke、marketplace smoke 和发布校验。

## 集中验收标准

- `tools/list` 精确暴露 15 个公共工具，风险分布为 4/10/1。
- 不公开 `inspect_route`、`propose_route_change` 或低层 capability 名。
- `execute_route_change` 仍是唯一 high-risk 工具。
- 所有公共推荐动作只引用真实可见的新工具和正确参数结构。
- package smoke、插件 smoke、Git marketplace smoke 和发布检查通过。
- workspace typecheck、lint、相关测试和 `git diff --check` 通过。
- canonical RouteLedger 数据模型和持久化 L3 `actionType` 未改变。

## 后续度量

上线前后应记录：工具名选择正确率、operation 选择正确率、首调用成功率、平均恢复轮次、缺失根目录断言比例、L3 顺序正确率、tools/list 总字节和各工具 Schema 大小。若总 Schema 成本仍影响宿主，应优先优化按需披露或描述结构，而不是重新把不同职责合并成宽泛工具。
